# AgentHub Frontend Implementation Task

你现在需要为 **AgentHub** 开发一套完整、现代、可维护的 Web 前端。

请不要把这个任务理解为“制作几个静态页面”。这是一个真实的开发者工具 / AI Workflow SaaS 前端，需要围绕现有后端 API、数据模型和工作流运行机制完成合理的前端架构、页面设计和交互实现。

你的目标是：

> 为 AgentHub 构建一个面向开发者的低门槛 AI Workflow 可视化开发平台，使用户可以通过拖拽、连接和配置节点构建 Agent Workflow，并管理模型、知识库、文档、工具和账户。

---

# 1. 开始开发前必须做的事情

首先阅读并理解仓库中的以下文件，并将它们视为后端行为的主要事实来源：

- `http.md`
  - 后端 HTTP API 文档
  - API path
  - request / response schema
  - enum
  - JWT authentication
  - Workflow / Node / Edge / Model / Knowledge Base / Tool / Session API
  - SSE workflow run API

- `tables.sql`
  - MySQL 表结构
  - 理解实体之间的关系
  - 不要为了前端方便而随意创造数据库不存在的业务实体

- `readme.md`
  - 理解 AgentHub 的整体定位、架构和运行方式

同时检查实际代码中的：

- route
- DTO
- request / response struct
- workflow node config
- workflow validation
- enum

如果文档与实际代码存在差异，以当前实际后端实现为最终依据。

不要修改后端代码，除非任务明确要求。

不要凭空创造后端 API。

如果某个 UI 功能目前没有对应 API：
1. UI 可以合理预留；
2. 将 API 调用抽象好；
3. 明确添加 TODO；
4. 不要伪造一个实际不存在的服务端接口。

# 12. React Flow 性能

这是一个交互密集页面，需要特别注意 rerender。

要求：

- `nodeTypes` 定义在 component 外部
- `edgeTypes` 定义在 component 外部
- handler 使用稳定 callback
- 不要让 node component 订阅整个 workflow store
- node 只读取自己需要的数据
- expensive selector 尽量保持细粒度
- 不要每拖动 1px 都请求后端
- 不要因为右侧 Inspector 一个输入框变化导致整个 Flow rerender

Node position：

拖动过程中只修改本地状态。

在：

```text
onNodeDragStop
```

后 PUT position。

必要时 debounce。


```text

   equals "approved"

```

# 23. Branch Handles

Branch Node 不应该只有一个普通 output。

每个 rule 都有自己的 source Handle：

```text
approved  ○
retry     ○
default   ○
```

Handle ID：

直接使用 rule ID。

默认 Handle：

```text
$default
```

创建 Branch outgoing edge 时：

edge config：

```json
{
  "branch_rule_id": "approved"
}
```

默认：

```json
{
  "branch_rule_id": "$default"
}
```

如果用户修改 Branch rule：

- handle 数量可能变化
- handle ID 可能变化

正确处理 React Flow dynamic handles，并同步 Node internals。

禁止用 index 作为 rule ID。

rule ID 必须稳定。

用户描述中希望模型包含：

```text

```

但是必须注意当前 backend contract。

如果：

- HTTP response 有 `provider`
- 但 create request / DTO 没有 `provider`
- database schema 也没有相应字段

则这是 backend contract mismatch。

处理原则：

**不要擅自向 API POST 一个 backend 不接受的 provider 字段。**

你应该：

1. 检查实际 DTO / service / model；
2. 如果当前 backend 已支持 provider，则加入 Provider Selector；
3. 如果没有，则 UI 暂时不提交 provider；
4. 在前端代码添加明确 TODO。

Provider 如果实际支持，可包括：

```text

Ark
```

并根据后端 enum 映射。

# 50. BigInt ID

后端数据库 ID 为 BIGINT。

注意 JavaScript `number` 的安全整数问题。

检查 JSON 中后端实际 ID serialization 方式。

如果后端可能产生超过：

```text
Number.MAX_SAFE_INTEGER
```

的雪花 ID：

前端最好将 ID 当作 string 处理。

不要对 ID 做数学运算。

React Flow 本身也使用 string id，非常适合直接规范化：

```ts
id: String(backendNode.id)
```

API path 中同样直接使用 string。

这是重要的工程要求。

# 51. API / UI Contract Gaps

当前文档中可能存在一些不完全一致之处。

必须主动检查实际代码，而不是猜。

尤其包括：

### Tool Subscription

POST 可以修改 subscription，但可能缺少 GET 当前 subscription 状态。

### Model Provider

对于这些问题：

- 隔离 workaround
